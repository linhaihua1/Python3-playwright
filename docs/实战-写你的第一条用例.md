## 零、先想清楚：这次要加什么用例

写代码前先用一句话说清"测什么、怎么算通过"。这次我们选：

| 项目 | 内容 |
|---|---|
| 测什么 | 素材库的**查询区**是否正常 |
| 具体步骤 | ① 已进入素材库 ② 三个关键控件都在 ③ 关键字能填进去、重置后能清空 |
| 判定标准 | 页面标题对 + 控件清单无缺失 + 读回来的值和填进去的一致 |
| 数据影响 | **零**。不点「查 询」（不发请求）、不点「上 传」「报 送」（不写数据） |

> **为什么特意挑一条"只读"用例当第一个练习？**
> 因为被测系统是**生产环境**。你第一次写用例，最该做的不是"跑通复杂业务"，
> 而是"在不出事的前提下，把写的→跑的→验证的整个闭环走一遍"。
> 只读用例随便跑，跑坏了也不会有任何后果。

**用哪套模板？** 这条用例自己完成登录、不依赖别的用例 → 用**独立用例**模板（自带浏览器）。

## 二、第 1 步：元素定位（查，而不是急着加）

### 2.1 正确习惯：先查元素表有没有

新手最容易犯的错是"上来就加一条 xpath"。正确做法是先搜一遍：

```bash
# 在工程根目录，搜你要操作的控件是不是已经有定位了
grep -n "查询\|keyword\|querybutton" Common/elementPage.py
```

本次要用的三个控件，**全部已存在**：

```python
# Common/elementPage.py -> class Element1
keyword     = ['xpath', "//*[@id='app']/div/div[2]/section/section/main/div[1]/form/div[2]/div/div/input"]  # 关键字输入框
querybutton = ['xpath', "//*[@id='app']/div/div[2]/section/section/main/div[1]/form/div[6]/div/button/span"]  # 「查 询」
replacement = ['xpath', "//*[@id='app']/div/div[2]/section/section/main/div[1]/form/div[7]/div/button"]        # 「重 置」
```

**所以第 1 步本次不用改文件。** 这是常态 —— 工程里已有的定位能覆盖大部分操作。

> ⚠️ 重复定义同一个元素是维护灾难：页面上只有一个「重 置」按钮，
> 却有两个变量名指着它，改版时你只会想起改其中一个。

### 2.2 确实需要新增时，怎么写

假设要操作一个还没登记的元素。**三步走**：

**① 用 F12 找到稳定特征**（不要直接抄浏览器给的绝对路径）

打开目标页 → F12 → 点左上角箭头 → 点你要操作的元素 → 看它的属性：

| 优先级 | 用什么 | 例子 | 稳定性 |
|---|---|---|---|
| 1 | `id` | `['id', 'global-uploader-btn']` | 最稳 |
| 2 | 可见文字 | `['xpath', "//span[normalize-space(.)='查 询']"]` | 很稳 |
| 3 | 语义明确的属性 | `['css', "input[placeholder='请输入关键字']"]` | 稳 |
| 4 | 相对 xpath | `['xpath', "//main/form//button"]` | 一般 |
| ❌ | 绝对路径 | `['xpath', "/html/body/div[4]/div/div[2]/..."]` | **别用**，多套一层 div 就失效 |

**② 加进元素表**（只加在这里）

```python
class Element1:
    # ...已有元素...

    # ==================== 素材库：删除素材 ====================
    # 「删 除」按钮：按可见文字定位，不依赖 DOM 层级
    # 注意按钮文字里通常带空格（前端为了排版加的），normalize-space 能吞掉多余空格
    delete_button  = ['xpath', "//button[.//span[normalize-space(.)='删 除']]"]
    confirm_delete = ['xpath', "//button[.//span[normalize-space(.)='确 定']]"]
```

**③ 立刻跑一下格式检查**（工程自带这个测试，专门防手滑）：

```bash
python tests/run_unit_tests.py tests.test_element_page
```

这条测试会校验每个元素都是 `[定位方式, 定位值]` 两个元素、
且定位方式必须是 `id / name / class / tag / link / plink / css / xpath` 之一。
写错格式当场报错，不会等到跑用例时才炸。

## 三、第 2 步：页面对象加动作

**位置**：`PageObject/loginPage.py` 的「四、关键字查询」段
**规矩**：只写动作，**不写断言**（`assertEqual` 之类一律不许出现）

本次新增 4 个方法，每个都很短：

```python
def query_form_ready(self):
    """自检：素材库查询区的关键控件是否都已渲染出来，返回检查结果。

    :return: dict，形如 {'关键字输入框': True, '查询按钮': True, '重置按钮': False}

    本方法**只读**：不点任何按钮、不发请求，因此可以安全地在生产环境执行。
    """
    checks = {
        '关键字输入框': Element1.keyword,
        '查询按钮': Element1.querybutton,
        '重置按钮': Element1.replacement,
    }
    result = {}
    for name, selector in checks.items():
        # timeout=0 表示立即判定，不等待：此时页面已经加载完，等下去没意义
        result[name] = self.get_element(selector, timeout=0) is not None
        log1.info('查询区控件[%s] 存在=%s' % (name, result[name]))
    return result


def fill_keyword(self, keyword):
    """只往关键字输入框里填内容，**不点查询**（只读操作，不产生数据影响）。"""
    self.type(Element1.keyword, keyword)


def read_keyword(self):
    """读取关键字输入框当前的值（校验输入是否生效、重置是否清空）。"""
    return self.get_value(Element1.keyword)


def reset_query(self):
    """点「重 置」清空查询条件，把列表恢复到初始状态。"""
    self.click(Element1.replacement)
```

### 这几行代码里，有 4 个新手必须理解的细节

**① `self.click` / `self.type` 是哪来的？**
`LoginPage` 继承自 `BasePage`，父类的方法直接就能用。你不用关心它们内部怎么调 Playwright。

**② 为什么 `get_element` 要传 `timeout=0`？**
`get_element` 默认会**显式等待**最多 15 秒（等元素出现）。这在"页面刚跳转"时是必须的；
但此处页面已经加载完了，再等就是白等。`timeout=0` 表示"立即判定，别等"。

**③ `get_element` 找不到元素返回的是 `None`，不是抛异常**
所以必须 `is not None` 判空。直接写 `self.get_element(...).click()` 会得到
`AttributeError: 'NoneType' object has no attribute 'click'` —— 新手最常撞的墙。

**④ `get_value` 和 `get_text` 别搞混**（这对最容易错）

| 方法 | 读什么 | 用在哪 |
|---|---|---|
| `get_text()` | 元素中间**显示的文字** | 按钮文案、标题、表格单元格 |
| `get_value()` | 控件的 **value 属性** | `input` / `textarea` / `select` |

输入框里填了字，它的 `.text` 是**空的** —— 想校验"值真的填进去了"只能用 `get_value()`。

> `get_value()` 是本框架原本**没有**的方法，这次实战才补上的。
> 详见 [第七节](#七实战中顺手修掉的一个真实-bug) —— 这属于"发现框架缺能力"时的正常操作。

## 四、第 3 步：用例层加用例

**位置**：新建 `TestSuites/testMaterialCheck.py`
**文件名硬性要求**：必须小写 `test` 开头（`testMaterialCheck.py` ✅ / `TestMaterialCheck.py` ❌ / `test-material-check.py` ❌）

### 4.1 完整代码（已存在于工程中）

```python
import unittest

from Common.basePage import BasePage
from Common.config import Config
from Common.log import log1
from PageObject.loginPage import LoginPage


class TestMaterialCheck(unittest.TestCase):
    """素材库查询区只读自检。"""

    driver = None

    # 断言期望值没有任何代码兜底：值只来自 config.ini -> [assert] title_material
    # （零硬编码纪律：缺配置会在 setUpClass 直接报错并指明该配哪个键）
    title_material = None

    @classmethod
    def setUpClass(cls):
        """类级前置：读配置 -> 开浏览器 -> 走完进入素材库的前置链路。"""
        # ---- 1. 从配置读参数（业务数据缺失即报错，绝不硬编码账号/标题）----
        cls.username, cls.password = Config.get_account()
        cls.title_material = Config.require('assert', 'title_material',
                                            '进入素材库后页面标题的期望值')

        # ---- 2. 打开浏览器 ----
        cls.base = BasePage()
        cls.driver = cls.base.open_browser()

        # ---- 3. 建页面对象 ----
        cls.page = LoginPage(cls.driver)

        # ---- 4. 前置链路：登录 -> 进生产系统 -> 切标签页 -> 进素材库 ----
        cls.page.login(cls.username, cls.password)
        cls.page.click_sign_in()          # 点「发布系统」，会新开标签页
        cls.page.switch_other_window()    # ★ 必须切到新标签页，否则后面全部定位失败
        cls.page.page_wait('workbench_render', 2)   # 等新页面首屏渲染（[timing] 可配）
        cls.page.click_material()         # 左侧菜单：内容管理 -> 素材库
        cls.page.page_wait('material_render', 2)    # 等素材库首屏渲染（[timing] 可配）

    @classmethod
    def tearDownClass(cls):
        """类级后置：关闭浏览器。放在这里能保证用例失败也照样关掉。"""
        cls.base.dr_quit()

    def check_title(self, case_name, expected):
        """断言当前页面标题等于预期值。"""
        actual = self.page.get_title()
        try:
            self.assertEqual(actual, expected)
        except AssertionError:
            log1.error('用例失败:%s，期望[%s] 实际[%s]\n' % (case_name, expected, actual))
            self.page.get_img()     # ★ 失败瞬间截图，这是排错最有效的证据
            raise

    def test_1ready(self):
        """用例1：前置链路走通 —— 已经停在素材库页面。"""
        case_name = '进入素材库'
        log1.info('执行测试用例：%s' % case_name)
        self.check_title(case_name, self.title_material)

    def test_2controls(self):
        """用例2：查询区的三个关键控件都渲染出来了。"""
        case_name = '查询区控件齐全'
        log1.info('执行测试用例：%s' % case_name)

        ready = self.page.query_form_ready()
        missing = [name for name, ok in ready.items() if not ok]

        if missing:
            self.page.get_img()
        self.assertEqual(missing, [], '素材库查询区缺少这些控件：%s' % missing)

    def test_3keyword(self):
        """用例3：关键字能真的填进去，重置后能真的清空。"""
        case_name = '关键字输入与重置'
        log1.info('执行测试用例：%s' % case_name)

        keyword = Config.require('testcase', 'query_keyword')

        # ---- 步骤 1：填值，然后读回来比对 ----
        self.page.fill_keyword(keyword)
        actual = self.page.read_keyword()
        self.assertEqual(actual, keyword,
                         '输入未生效：期望填[%s]，实际读到[%s]' % (keyword, actual))

        # ---- 步骤 2：重置，再读回来确认已清空 ----
        self.page.reset_query()
        self.page.page_wait('reset_settle', 1)   # 等前端清空输入框（[timing] 可配）
        cleared = self.page.read_keyword()
        self.assertIn(cleared, (None, ''), '重置后关键字输入框应被清空，实际=[%s]' % cleared)
```

### 4.2 逐点拆解：每一处为什么这么写

**① 类必须继承 `unittest.TestCase`，类名必须 `Test` 开头** —— 否则不会被收集。

**② 方法名 `test_1ready` 里的数字不是装饰，是**执行顺序

unittest 按方法名字母序执行。加数字前缀就是为了**固定顺序**。
不加数字的话，顺序按拼音/字母排，你的用例可能先跑"重置"再跑"输入"，结果必错。

> 反过来说：**改方法名 = 改执行顺序**，可能让本来通过的用例失败。

**③ 参数一律从 `Config` 读，一个都不硬编码**

```python
cls.username, cls.password = Config.get_account()
keyword = Config.require('testcase', 'query_keyword')
cls.title_material = Config.require('assert', 'title_material',
                                    '进入素材库后页面标题的期望值')
```

读取方式分两种，对应两条纪律（零硬编码改造后全框架统一）：

- **业务数据**（账号、路径、断言期望值……）用 `Config.require(段, 键)` ——
  **代码里不写任何兜底值**，配置缺失立刻抛 `ConfigMissingError`，
  报错文案直接给出「段 + 键 + 对应环境变量 + 该键含义」，runner 判退出码 2。
  这比"带空值继续跑、最后在莫名其妙的地方失败"好排查得多。
- **技术参数**（超时、间隔、开关）才用 `Config.get(段, 键, 默认值)`，
  兜底值是技术默认值，不配也能跑。

**④ `setUpClass` 只开一次浏览器，`tearDownClass` 负责关掉**

- 用 `@classmethod` 的 `setUpClass` / `tearDownClass`：整个类**只执行一次**。
- 对比 `setUp` / `tearDown`：**每条用例都执行一次**（3 条用例就开 3 次浏览器，慢且浪费）。

`tearDownClass` 里必须关浏览器，否则会残留一堆 `chrome.exe` 进程。

**⑤ ★ `switch_other_window()` 忘了写 = 后面全部定位失败**

点「发布系统」会**新开一个标签页**，但 `BasePage` 手上的操作句柄（Playwright 的 Page 对象）还停在旧标签页上。
不切过去的话，你在新页面上找任何元素都找不到 —— 这是本工程**最容易踩的坑**。

**⑥ 断言要能"说清哪里错了"**

对比这两种写法：

```python
# ❌ 失败时只告诉你"有东西少了"，不说少哪个
self.assertTrue(all(ready.values()))

# ✅ 失败信息直接可用
missing = [name for name, ok in ready.items() if not ok]
self.assertEqual(missing, [], '素材库查询区缺少这些控件：%s' % missing)
```

**⑦ 断言失败要留下证据**

```python
except AssertionError:
    log1.error('用例失败:%s，期望[%s] 实际[%s]\n' % (case_name, expected, actual))
    self.page.get_img()     # 截图
    raise                   # 重新抛出，让 unittest 记为"失败"
```

`raise` 不能漏 —— 漏了就变成"记了日志但用例显示通过"，比不截图还危险。

**⑧ `assertIn(cleared, (None, ''))` 为什么这么写**

不同前端框架，重置后 `value` 可能是空串 `''`，也可能是 `None`。两种都算"已清空"，
所以用 `assertIn` 而不是 `assertEqual(cleared, '')`。

## 五、第 4 步：验证（这一步最容易被新手跳过）

### 第 1 级：确认用例被收集到（零风险，1 秒）

> 本工程的 `config.ini` 模板里是占位符（`your_username`），
> 而 `[environment] url` 可能指向**生产环境**。本次演示的用例是只读的，
> 但如果你抄的是 `testLogin.py` 那种会真实上传、报送数据的用例，跑之前务必想清楚。

**跑完四处产物（排错按这个顺序看）：**

| 想看什么 | 去哪看 |
|---|---|
| 失败摘要（最快） | 控制台输出 |
| 失败原因（带模块名+行号） | `Logs/当天日期/Error_Logs/*.log` |
| 失败瞬间页面长什么样 | `img/当天日期/*.png` |
| 完整报告 | 浏览器打开 `Report/*.html` |

## 六、第 5 步（进阶）：给新用例加结构单测

**这一步不是必须的，但强烈建议。** 为什么？

UI 用例本身要开浏览器、连真实环境，没法在单元测试里跑。
但用例的**结构约定**恰恰是"最容易被后来人改坏、坏了又最难发现"的部分：

- 方法名顺序被改 → 执行顺序变了 → 用例开始莫名失败
- 有人往里加了写操作 → 这条"只读用例"不再安全 → 在生产环境跑就出事了
- 前置链路里有人删了 `switch_other_window` → 整条用例全崩

本次新建的 `tests/test_test_material_check_suite.py` 就把这些钉死了：

```python
class TestReadOnlyGuarantee(unittest.TestCase):
    """★ 只读保证：这条用例能在生产环境安全执行，靠的就是下面几条。"""

    def test_不出现任何写操作(self):
        source = inspect.getsource(check_suite)
        for banned in ('upload_file', 'fill_upload_form', 'submitted', 'save'):
            self.assertNotIn(
                banned, source,
                '一旦引入写操作（%s），本用例就不再是只读的，'
                '必须重新评估能否在生产环境执行' % banned,
            )

    def test_前置链路包含切换标签页(self):
        source = inspect.getsource(TestMaterialCheck.setUpClass)
        self.assertIn('switch_other_window', source,
                      '前置链路缺少切换标签页，进了生产系统也无法操作')
```

再加几条"参数是否真的来自配置"的检查 —— 零硬编码之后这类检查更简单了：
代码里**根本没有**默认标题，只要 mock 出一份**带不同值**的测试配置，断言取到的就是配置值：

```python
CHECK_INI = """\
[testcase]
login_username = unit_user
login_password = p%ss%word
query_keyword = 单元关键字

[assert]
title_material = 配置里的素材库标题     # ← 代码里没有任何兜底值可比，只能是它来自配置
"""

def test_期望标题来自配置(self):
    self._run_with_fakes()
    self.assertEqual(TestMaterialCheck.title_material, '配置里的素材库标题')
```

配得再配上一条反向检查（`tests/test_test_material_check_suite.py` 里就是这么做的）：
mock 的 `Config.require` 抛 `ConfigMissingError` 时，`setUpClass` 必须原样炸出去 ——
证明缺配置时**绝不会**带着 `None` 往下跑。

> ⚠️ **写这种测试有个必踩的坑**：它 import 了真实的 `TestMaterialCheck` 类，
> 而 unittest 会把模块里**所有** `TestCase` 子类都当成用例运行 ——
> 那样 `setUpClass` 会真的去打开浏览器连生产环境。
> 解决办法：在文件末尾定义 `load_tests()` 白名单，显式声明"本文件只跑这几个类"。
> 现成写法见 `tests/test_test_login_suite.py` 和 `tests/test_test_material_check_suite.py`。

## 七、实战中顺手修掉的一个真实 Bug

写这条用例的过程中，用了 `get_value()` —— 但框架里**没有这个方法**。

这很正常。**新手遇到"框架没有我要的能力"时，正确做法不是绕过去，而是补上它。**
补的时候会顺带发现一些真实缺陷，本次就抓到一个：

### 7.1 缺陷：`Config.getint` 这个方法根本不存在

`PageObject/genericPage.py` 的通用登录里有一行：

```python
# ❌ 错误
self.get_element_by_text(success_text, timeout=Config.getint('ci', 'element_timeout', 15))
```

正确的方法名是 `Config.get_int`（带下划线）。写成 `getint` 会直接抛：

```
AttributeError: type object 'Config' has no attribute 'getint'
```

**为什么这个错能潜伏这么久？** 因为它在一个**很少走到的分支**里：

```python
if success_text:
    ...Config.getint(...)   # ← 只有 [system] success_text 配置了才会执行
else:
    self.wait_loading_gone()
```

而工程默认配置里 `success_text =`（空），所以本地怎么跑都不会触发。
**只有当你按文档去接入一个新系统、填了成功标识，才会突然炸。**

> 这正好说明[第六步](#六第-5-步进阶给新用例加结构单测)的价值：
> 一个分支没有测试覆盖，就等于"没人检查过它是死是活"。

### 7.2 修复

```python
# ✅ 正确
self.get_element_by_text(success_text, timeout=Config.get_int('ci', 'element_timeout', 15))
```

> 📌 **后续演进（零硬编码改造）**：这一行后来又简化成 `timeout=self.timeout` ——
> `BasePage` 在 `__init__` 时已经从 `[ci] element_timeout`（技术参数，带默认 15）
> 读好并统一注入 Playwright 的默认动作超时，页面方法不再各自现取配置。
> 同时该文件里的账号、占位符文案、按钮文字全部改成了 `Config.require`
> （业务数据没配就直接报错），只有 `success_text` 和菜单渲染等待
> （`Config.get_float('tuning', 'menu_render_wait', 1)`）保持"允许缺省"的技术语义。

### 7.3 补上回归测试（关键的一步）

只修代码不补测试，同样的错还会再来一次。本次补了两条：

```python
class TestGenericLoginSuccessText(unittest.TestCase):
    """success_text 非空 -> 走「等成功标识出现」而不是「等加载遮罩消失」。"""

    INI = """\
[ci]
element_timeout = 9

[system]
username_placeholder = 请输入用户名
password_placeholder = 请输入密码
login_button_text = 登录
success_text = 退 出
"""

    def test_配置了成功标识时按其等待且不报错(self):
        """★ 回归保护：本分支曾把 Config.get_int 误写成 Config.getint。"""
        ...

    def test_Config的整数读取方法名是get_int(self):
        """明确钉住方法名：Config 没有 getint()。"""
        self.assertTrue(hasattr(Config, 'get_int'))
        self.assertFalse(hasattr(Config, 'getint'))
```

### 7.4 **验证测试真的有效**（这一步千万别省）

写了个测试，怎么知道它真能抓到 bug？**把修复临时改回去，看它红不红。**

把 `get_int` 改回 `getint`，跑一次：

```
ERROR: test_配置了成功标识时按其等待且不报错
AttributeError: type object 'Config' has no attribute 'getint'
FAILED (errors=1)
```

红得干脆、错误信息直指原因。改回来，恢复绿。

> **写测试的铁律：先确认它在"错误的世界"里会失败，才算数。**
> 一个永远绿的测试，比没有测试更危险 —— 它给你虚假的安全感。

## 八、新手最该记住的 5 句话

1. **用例层管断言，页面对象管动作，基类管操作，元素表管定位。**
   写代码前先问自己"这行属于哪一层"，放错层就是给自己挖坑。

2. **能读配置的，绝不写死。** 账号、地址、标题、路径、关键字 —— 全部走 `config.ini`。
   业务数据用 `Config.require`（**没配就报错**，报错自带"该配哪个键"的线索），
   技术参数用 `Config.get(…, 默认值)`；等待秒数走 `page_wait()` + `[timing]`。

3. **"没报错"不等于"生效了"。** 必须把值读回来比对（`get_value`），
   才叫真的验证过。这条能帮你避开大半的"假成功"。

4. **写完先跑两级验证**：收集校验（确认被收到）→ 框架单元测试（确认没改坏框架）→ 最后才真跑。
   顺序反了，出了问题你不知道该怀疑用例、框架还是环境。

5. **改了东西就跑 `python tests/run_unit_tests.py`。**
   30 秒，不开浏览器，能帮你把"框架坏了"和"页面改版了"两类问题彻底分开。
