## 一、工程概览

### 1.1 一句话说明

基于 **unittest + Playwright + PageObject 分层**的 Web UI 自动化工程，用 6 条串行用例走完
「统一门户登录 → 进入融媒体生产系统 → 素材库 → 上传视频 → 关键字查询 → 报送」整条业务链，
输出**中文 HTML 测试报告**（给人看）与 **JUnit XML 结果**（给流水线看）。

### 1.2 技术栈

| 项 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.9+ | 实测 3.11.9 通过 |
| 测试框架 | unittest（标准库） | 不引入 pytest，保持零额外依赖 |
| 浏览器驱动 | Playwright（`playwright.sync_api`） | 自带浏览器与驱动管理，**无需手工放置任何浏览器驱动**；`pip` 装完执行一次 `python -m playwright install chromium` 即可 |
| 设计模式 | PageObject | 用例 / 页面对象 / 基类 / 元素表 四层分离 |
| 报告 | 内置 `HTMLTestReportCN` + 自研 `junitReport` | 一次执行同时产出两种报告 |
| CI | Jenkins（声明式流水线） | 见根目录 `Jenkinsfile`，也支持容器化运行 |

## 二、整体架构与调用链

### 2.1 四层分层

```
┌─────────────────────────────────────────────────────────────┐
│ 入口层      run.py / entrance.py                             │
│             只做两件事：解析参数、把参数转成配置覆盖           │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 执行层      Common/runner.py                                  │
│             收集用例 → 执行 → 出报告 → 返回退出码              │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 用例层      TestSuites/testLogin.py                           │
│             写业务步骤 + 断言（本工程断言=校验页面标题）        │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 页面对象层  PageObject/loginPage.py                           │
│             一个方法 = 一个业务动作（登录、进素材库、报送…）    │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 基础层      Common/basePage.py  +  Common/elementPage.py      │
│             +  config.ini [locators]（界面文案）              │
│             basePage：怎么操作浏览器（唯一直接调 Playwright）    │
│             elementPage：定位策略（界面文案在 [locators] 配置）│
└─────────────────────────────────────────────────────────────┘

横切支撑：config.py（配置）· log.py（日志）· dir_config.py（路径）
          junitReport.py（CI 结果）· ci.py（CI 上下文）· sentMail.py（通知）
```

**分层铁律**（写新代码时请遵守）：

| 层 | 允许做的事 | 禁止做的事 |
|---|---|---|
| `TestSuites/` | 调页面对象方法、写断言 | 不写 xpath、不直接操作元素 |
| `PageObject/` | 一个方法 = 一个业务动作 | 不写断言、不出现 xpath 字符串 |
| `Common/basePage.py` | 封装浏览器与元素操作 | 不掺业务逻辑 |
| `Common/elementPage.py` | 只放定位策略（怎么找） | 不放界面文案、不放业务代码 |

一句话：**用例层管断言，页面对象管动作，基类管操作，元素表管定位策略，界面文案进配置。**

### 2.2 关键调用链（自上而下）

```
run.py
 └─ apply_runtime_overrides()        命令行参数 → UI_* 环境变量
 └─ runner.run()
     ├─ ci.log_context()             记录构建上下文（Jenkins 上能看出是哪个构建）
     ├─ resolve_case_filter()        决定跑全量还是冒烟子集
     ├─ build_suite()
     │   ├─ unittest.defaultTestLoader.discover(TestSuites, top_level_dir=工程根)
     │   └─ filter_suite()           冒烟时按关键字过滤
     ├─ HTMLTestRunner(resultclass=JUnitResult).run(suite)
     │   └─ 逐条执行 TestSuites/testLogin.py
     │       └─ setUpClass：BasePage.open_browser() 开浏览器
     │       └─ 每条用例：LoginPage.xxx()
     │           └─ BasePage.type/click/get_element  →  playwright.sync_api（Locator）
     │           └─ 元素定位来自 elementPage 策略 + [locators] 配置
     │       └─ tearDownClass：BasePage.dr_quit() 关浏览器
     ├─ junitReport.write_junit_xml()   写 Report/junit-results.xml
     ├─ sentMail.sent_mail()            （可选，--mail 时）
     └─ 返回汇总字典（含 exit_code）
 └─ print_conclusion() → sys.exit(exit_code)
```

### 2.3 在框架里改东西，该改哪个文件？

| 想做的事 | 改哪里 |
|---|---|
| 改业务步骤、加断言 | `TestSuites/testLogin.py` |
| 改页面操作方式 | `PageObject/loginPage.py` |
| 页面改版、元素找不到 | `config.ini [locators]`（文案）/ `Common/elementPage.py`（策略） |
| 加新的浏览器操作能力 | `Common/basePage.py` |
| 换环境、换账号、换上传文件 | `config.ini`（或环境变量） |
| 改报告标题/文件名 | `config.ini [report]` 或 `run.py --title/--filename` |
| 改日志格式/位置 | `Common/log.py` |
| 改流水线行为 | `Jenkinsfile` |

## 三、一次运行的完整执行时序

以 `python run.py --suite smoke` 为例，逐步说明发生了什么：

| 步骤 | 执行内容 | 产出/日志 |
|---|---|---|
| 1 | `run.py` 解析命令行参数 | — |
| 2 | `apply_runtime_overrides()` 把 `--headless` 等转成 `UI_CI_HEADLESS` 环境变量 | `命令行覆盖配置：headless=True` |
| 3 | `runner.run()` 启动，`ci.log_context()` 打印运行环境 | `运行环境：CI=False \| 任务=- \| ...` |
| 4 | 读报告元信息：标题、报告名、执行人、描述（`Config.require('report', …)`，**没配直接 ABORTED**）；CI 上自动把构建号拼进报告描述 | — |
| 5 | `resolve_case_filter('smoke')` 读 `[ci] smoke_cases` → 得到 3 个关键字 | `冒烟测试模式，用例过滤关键字：[...]` |
| 6 | `build_suite()` 扫描 `[paths] testcases_dir`（默认 `TestSuites/`），按 `[paths] case_pattern`（默认 `test*.py`）收集到 6 条用例 | `加载测试用例完成，共 6 个用例` |
| 7 | `filter_suite()` 按关键字过滤，命中 3 条 | `用例过滤：关键字=[...]，命中 3/6 条` |
| 8 | 创建 `Report/xxx.html`，`HTMLTestRunner(resultclass=JUnitResult)` 执行 suite | — |
| 9 | **`setUpClass`**：`Config.get_account()` + `Config.require` 读文件路径/关键字/手机号等，再 `Config.require('assert', 'title_*')` 读三个断言标题（**任一缺失立刻报错并指明该配哪个键，退出码判 2**）→ `BasePage.open_browser()` 起浏览器（视口/语言取 `[tuning]`）→ 建 `LoginPage` 实例 | `打开chrome浏览器（无头=True，视口=1920x1080）` |
| 10 | **`test_1login`**：填账号密码 → 点登录 → 校验标题 = `[assert] title_login` 的配置值 | `测试用例执行成功:登录成功` |
| 11 | **`test_2select_scxt`**：点「发布系统」→ **切到新标签页** → 校验标题 | 同上 |
| 12 | **`test_3material`**：内容管理 → 素材库 → 校验标题 | 同上 |
| 13 | **`tearDownClass`**：`dr_quit()` 关闭浏览器 | `关闭浏览器` |
| 14 | 关闭 HTML 文件句柄，报告落盘 | `测试执行结束，HTML 报告生成成功` |
| 15 | `write_junit_xml()` 生成 JUnit XML | `JUnit XML 已生成：...（用例 3，失败 0 ...）` |
| 16 | 有失败则打印失败摘要（控制台） | `==================== 失败摘要 ====================` |
| 17 | `print_conclusion()` 打印结论块，`sys.exit(exit_code)` | `退出码 : 0` |

> ★ 第 3 步到第 7 步是**准备工作**，第 8 到 13 步是**真正跑用例**，第 14 到 17 步是**结果输出**。
> 排查问题时先确认卡在哪一段：准备阶段失败看配置，执行阶段失败看元素定位，输出阶段失败看磁盘权限。

## 四、模块详解

### 4.1 入口层

#### `run.py` —— 主入口（新人阅读顺序：第 1 个）

**职责**：解析命令行参数 → 转成 `UI_*` 环境变量 → 调用 `runner.run()` → 按退出码 `sys.exit()`。

**关键函数**：

| 函数 | 作用 |
|---|---|
| `parse_args()` | 定义全部命令行参数（见 [5.2 参数表](#52-命令行参数)） |
| `apply_runtime_overrides(args)` | 把参数转成环境变量，交给 config 的覆盖机制 |
| `print_conclusion(summary)` | 打印结论块，流水线日志一眼可见 |

**为什么参数走环境变量**：全工程只有一条配置优先级链路 ——
`显式传参 > 环境变量 > config.ini > （技术参数的）代码默认值`。命令行只是这条链路的入口，
这样「本机加参数跑」和「Jenkins 设环境变量跑」的行为完全一致，不需要维护第二套优先级逻辑。

#### `entrance.py` —— 备用入口

与 `run.py` 平行，区别只是报告标题/描述改从 `config.ini -> [entrance]` 读取
（零硬编码改造后，这里不再写死任何业务标题；`[entrance] title` 没配则启动即报错）。
支持 `python entrance.py smoke`。业务上已无必需，保留兼容。

#### `getcwd.py`

返回工程根目录（`os.path.dirname(os.path.abspath(__file__))`）。
被 `Common/log.py`、`Common/config.py` 使用。

---

### 4.2 执行层

#### `Common/runner.py` —— 执行器（新人阅读顺序：第 2 个）

**职责**：整个流程的"发动机"。收集用例 → 执行 → 出两种报告 → 判定退出码。

**关键函数**：

| 函数 | 作用 | 新人注意 |
|---|---|---|
| `build_suite(tests_dir, pattern, cases)` | 扫描用例目录并（可选）过滤 | `discover` **必须**传 `top_level_dir=工程根`，否则 `from Common.xxx import` 会失败 |
| `filter_suite(suite, keywords)` | 按用例方法名过滤（冒烟用） | 过滤结果必须是**串行链的前缀**，不能随便挑中间几条 |
| `resolve_case_filter(suite_kind, cases)` | 把 `full/smoke/自定义` 翻译成关键字列表 | — |
| `resolve_junit_path(junit)` | 决定 JUnit XML 输出路径 | 传 `none` 可关闭生成 |
| `print_failure_digest(result)` | 打印失败用例一行摘要到控制台 | Jenkins 控制台直接可见，不用打开报告 |
| `run(...)` | 主流程 | 返回汇总字典（含 `exit_code`） |

**退出码约定（CI 判定构建成败的依据）**：

| 退出码 | 含义 | 流水线表现 |
|---|---|---|
| `0` | 全部通过 | 构建成功 |
| `1` | 有用例失败或出错 | 构建失败（用例级问题） |
| `2` | 环境/配置问题（未收集到用例、地址没配、浏览器起不来、**必填业务配置缺失**） | 构建失败（需要人工介入环境/补配置） |

**返回的汇总字典**：

```python
{
  'exit_code': 0,           # 退出码，见上表
  'success': True,          # exit_code == 0 的快捷判断
  'tests_run': 3,           # 用例总数
  'failures': 0, 'errors': 0, 'skipped': 0,
  'report': '.../Report/xxx.html',      # HTML 报告路径
  'junit': '.../Report/junit-results.xml',  # JUnit XML 路径（未生成时 None）
  'duration': 83.4,         # 总耗时（秒）
  'cases': [ {classname, name, status, time, message, detail}, ... ]
}
```

### 4.3 用例层

#### `TestSuites/testLogin.py` —— 主用例集（**最该先读的文件**）

**被测业务链**：

```
统一门户(登录)  →  融媒体生产系统(工作台)  →  素材库  →  上传 / 查询 / 报送
 title:统一门户     title:工作台-云媒资系统     title:素材库-云媒资系统
```

**6 条用例**：

| 方法名 | 做什么 | 断言（页面标题，期望值全部来自 `[assert]` 配置） | 有副作用？ |
|---|---|---|---|
| `test_1login` | 输入账号密码登录 | `title_login` | 无 |
| `test_2select_scxt` | 点「发布系统」并切到新标签页 | `title_workbench` | 无 |
| `test_3material` | 内容管理 → 素材库 | `title_material` | 无 |
| `test_4uplaodbutton` | 选视频 → 填作者/手机号/上报单位 → 上传 → 确定 | 标题未跳走（仍是 `title_material`） | **上传视频** |
| `test_5keyword` | 关键字查询 → 重置 | 标题未跳走 | 无 |
| `test_6submitted` | 刷新 → 报送 → 选初审人 → 保存 | 标题未跳走 | **提交报送单** |

**三条设计约定（务必理解）**：

1. **6 条用例共用同一个浏览器**：它们是**一条串行业务流**，第 4 步上传依赖第 3 步的登录态。
   做法是 `setUpClass` 只开一次浏览器、`tearDownClass` 统一关闭，比每条用例重开快得多也稳得多。
2. **方法名的数字前缀是为了固定顺序**：unittest 默认按方法名字母序执行，
   `test_1` ~ `test_6` 就是这个作用。**改方法名会改变执行顺序，进而让用例失败**。
   同时这也意味着**不能单独跑中间某一条**（比如只跑 `test_5keyword`，它没有登录态）。
3. **断言统一收敛在 `check_title()`**：6 条用例的断言方式相同（校验标题），
   统一后只需在一个地方加"失败自动截图"。新增用例直接调 `self.check_title('用例名', '期望标题')`。

**参数来源**：账号、上传文件路径、表单字段、查询关键字、三个断言标题，全部在 `setUpClass` 里用
`Config.get_account()` / `Config.require(...)` 从 `config.ini` 读取 —— 用例代码里**零硬编码**，
任何一项没配都会在启动时报错并指明该配哪个键，绝不会带着空值误跑。

### 4.4 页面对象层

#### `PageObject/loginPage.py`

**职责**：把"登录门户"和"素材库"两个页面的操作写成人话级方法。`LoginPage` 继承 `BasePage`。

| 方法 | 对应业务动作 |
|---|---|
| `login(username, password)` | 统一门户填账号密码并登录 |
| `click_sign_in()` | 点「发布系统」（**会新开标签页**） |
| `click_material()` | 侧边菜单：内容管理 → 素材库 |
| `upload_file(file_path)` | 选择本地视频（默认直接给隐藏 `input[type=file]` 赋文件路径；失败回退 autoit） |
| `fill_upload_form(author, phone, reporting)` | 填表单 → 上传 → 收起列表 → 确定 |
| `keyword_query(keyword)` | 关键字查询 → 重置 |
| `submitted()` | 报送：开初审下拉 → 选初审人 → 保存 |

**为什么叫 `LoginPage` 却包含素材库操作**：这两个页面属于同一条业务链（门户 → 生产系统 → 素材库），
元素与跳转关系紧密，放一起比拆成三个文件更好维护。文件名为历史命名。

#### `PageObject/homePage.py`

空壳占位，`HomePage` 类无方法、无引用，**可删**。

#### `PageObject/genericPage.py` —— 通用页面对象（接入新系统的第一选择）

**职责**：不为某个系统写死元素，而是靠 `config.ini` 的"文案特征"驱动定位 ——
`[system] username_placeholder / password_placeholder / login_button_text`（**必填三项**，
`Config.require` 读取、缺配即报错）在页面上找输入框和登录按钮，`[system] success_text` 判登录成功。
换系统（党政/ERP/商城……）通常只改配置就能登录；`click_menu('内容管理', '素材库')` 之类的
逐级点菜单也按文本定位。复杂系统再升级为专属 PageObject + elementPage。

#### `TestSuites/testMaterialCheck.py` —— 只读自检用例集（3 条）

与 testLogin 不同：它**不做任何写操作**（无上传/报送），只做"登录链路通 + 素材库控件齐 +
输入/重置生效"三项体检，可以安全地在生产环境执行。断言标题同样只认 `[assert]` 配置；
前置链路放在 `setUpClass` 一次走完，各步骤等待走 `page_wait()`（`[timing]` 可配）。

### 4.5 基础层

#### `Common/basePage.py` —— 测试基类（唯一直接调 Playwright 的文件）

**六类能力**：

| 分类 | 方法 | 状态 |
|---|---|---|
| 浏览器生命周期 | `open_browser()` / `dr_quit()` | 在用 |
| 元素定位 | `get_element()` / `_parse_selector()` / `scroll_into_view()` / `js_click()` | 在用 |
| | `get_elements()` / `wait_element()` / `isdisplayed()` | 预留 |
| 常用交互 | `type()` / `click()` / `get_title()` / `page_wait()` / `refresh()`（page.reload） | 在用（`page_wait('键', 默认秒)` 读 `[timing]` 配置，等待时长不写死在用例里） |
| | `my_sleep()`（page_wait 的底层）、`input_enter()` / `get_text()` / `use_js()` | 在用 / 预留 |
| 窗口 / frame | `switch_other_window()` | 在用（新标签页注册有毫秒级延迟，内部轮询等待至 `element_timeout` 超时才判"没有其他窗口"） |
| | `switch_menue()` / `switch_iframe()` / `switch_default_content()` / `get_handle()` | 预留 |
| 文件上传 | `files_upload()`（**推荐**，走 `input[type=file]` 赋值） | 在用 |
| | `upload_by_autoit()`（降级兜底，需 `pip install PyAutoIt`） | 在用（降级分支） |
| 截图 / 弹窗 | `get_img()` / `popout()` | 在用 / 预留 |

> 标注为「预留」表示当前没有用例调用，属于框架能力储备 —— 改动前先全局搜索确认。

**元素定位写法**：统一用「二元列表」描述，格式 `[定位方式, 定位值]`：

```python
['xpath', "//input[@type='text']"]     # 用户名输入框
['id', 'global-uploader-btn']          # 按 id 定位
```

支持的定位方式见 `BY_MAP`：`id / name / class / tag / link / plink / css / xpath`。

**重要行为**：
- `get_element()` 返回的是 Playwright 的 **`Locator`（惰性定位器）**：此刻不保证元素已在页面，
  每个动作（click/fill/…）在执行瞬间才真正定位并自动等待就绪，**DOM 刷新后也永不过期、无需重新定位**。
  **找不到元素返回 `None` 而不抛异常** —— 调用方必须判空。
- `click()` 内部流程：定位（带等待）→ 滚动到可视区 → 原生点击 → 失败降级 JS 点击。
- `open_browser()` 支持**无头模式**（`[ci] headless`）。无头由 Playwright 原生 `headless` 参数控制，
  启动时附加稳健参数 `--no-sandbox --disable-gpu --disable-dev-shm-usage --hide-scrollbars`
  （有界面时改用 `--start-maximized`），窗口尺寸由浏览器上下文的 `viewport` 控制
  （`[tuning] viewport` 可配，默认 1920×1080；浏览器语言用 `[tuning] browser_locale`，默认 zh-CN）。

#### `Common/elementPage.py` —— 元素表（策略层 + 配置驱动）

**界面文案（按钮文字、菜单名、placeholder 关键词）已全部下沉到 `config.ini` 的
`[locators]` 段**，代码里零业务文案。`elementPage.py` 只保留**定位策略**——
"怎么按文字/属性/id 找元素"，可被所有系统复用，换系统不需要改它。

按业务分站组织：门户登录 → 系统入口 → 素材库导航 → 上传 → 查询 → 报送。

**三级取值优先级**（每个元素都按这个顺序解析）：

| 级 | 来源 | 什么时候用 |
|---|---|---|
| 1 | 配置给了 `<键名>_xpath` 完整表达式 | 业务想完全自定义定位（逃生门） |
| 2 | 配置给了 `<键名>` 界面文字 | **常规路径**：框架用策略函数现场拼 xpath |
| 3 | 代码里的技术兜底（`input[type=password]` 等） | 配置漏填时的安全网，通用 HTML 语义 |

**内置策略函数**（都在 `elementPage.py`，可组合复用）：

| 函数 | 行为 | 典型用途 |
|---|---|---|
| `by_text(text)` | 按可见文字**等值**匹配（跨 button/a/span/div） | 菜单项「内容管理」 |
| `by_text_loose(text)` | 先**剔除字间空格**再匹配 | 按钮「报 送」「查 询」——页面排版加的空格不影响 |
| `by_placeholder(*kws)` | 按 placeholder 包含关键词 | 输入框「关键字」 |
| `by_id_anchor(id, inner)` | 按 id 锚点取元素/内部标签 | 上传按钮 `global-uploader-btn` |

**两个来自真实浏览器实测的防护**（理解了能少踩很多坑）：

1. **`not(*)` 排除祖先容器**：页面上「登录」按钮外常包一层 div 做样式，
   xpath 的 `|` 联合按文档顺序返回，div 排在 button 前面——不加 `not(*)`
   会点到一个空壳 div，元素"找到了"动作却没生效。
2. **多分支优先取首个**：定位表达式常写成 `精确分支 | 兜底分支` 的联合，
   `BasePage._pick_target` 会先单独试首个分支（调用方真正想要的），
   命中就用它，而不是文档顺序更靠前的容器。

页面改版排查顺序：先查 `[locators]` 文案是否与页面一致（90% 是这个），
再考虑是否需要给该元素配 `<键名>_xpath` 精确表达式。

### 4.6 支撑层

#### `Common/config.py` —— 配置读写（CI 的配置注入靠它）

**两种读取方式，对应零硬编码纪律的两类数据**：

| 方法 | 用于 | 取不到时 |
|---|---|---|
| `Config.get('段','键',默认值)` / `get_int` / `get_float` / `get_bool` | **技术参数**（超时、间隔、视口、目录名） | 返回默认值，**不抛异常**（不配也能跑） |
| `Config.require('段','键')` / `require_int` / `require_float` | **业务数据**（标题、账号、路径、报告元信息、邮件文案） | 抛 `ConfigMissingError`，文案直接给出「段 + 键 + 对应环境变量 + 该键含义」，绝不带空值往下跑 |

**取值优先级：显式传参 > 环境变量 > config.ini > （技术参数的）代码默认值**

环境变量映射规则：`UI_` + 段名 + `_` + 键名，全大写，非字母数字转下划线。

| 配置项 | 环境变量 |
|---|---|
| `[environment] url` | `UI_ENVIRONMENT_URL` |
| `[environment] browser` | `UI_ENVIRONMENT_BROWSER` |
| `[testcase] login_username` | `UI_TESTCASE_LOGIN_USERNAME` |
| `[testcase] login_password` | `UI_TESTCASE_LOGIN_PASSWORD` |
| `[testcase] upload_file` | `UI_TESTCASE_UPLOAD_FILE` |
| `[assert] title_login` | `UI_ASSERT_TITLE_LOGIN` |
| `[ci] headless` | `UI_CI_HEADLESS` |
| `[ci] smoke_cases` | `UI_CI_SMOKE_CASES` |
| `[timing] menu_load` | `UI_TIMING_MENU_LOAD` |
| `[tuning] viewport` | `UI_TUNING_VIEWPORT` |

要整体关闭该机制：设 `UI_ENV_OVERRIDE=false`。

**业务便捷方法**：`get_account()`（require 两个账号键）、
`get_upload_file()`（默认 require；传 `required=False` 保留"取不到返回 None"的旧语义）。

#### `Common/configOverWriter.py`

定制版 `ConfigParser` 子类，只做两件事：
① 保留键名大小写（默认会全转小写，导致 `[addressed]` 段的中文键取不到）；
② **关闭 `%` 插值**（否则密码/路径里出现 `%` 会直接抛异常）。

#### `Common/log.py` —— 日志

`log1` 单例，同时写三处：

```
Logs/日期/
  ├─ All_Logs/2026-09-25 120718.log    所有级别
  └─ Error_Logs/2026-09-25 120718.log  仅 ERROR，且带模块名+行号，排错优先看它
控制台                                  实时输出
```

**注意**：① 别用 `print` 打业务日志（文件里没有，事后无法回溯）；
② `logging` 不支持 `log1.info('a:', b)` 多参数写法，必须拼字符串；
③ 打异常必加 `exc_info=1`，否则只有一行错误信息、没有堆栈。

**日志目录可挪走**：设环境变量 `UI_LOG_DIR` 即可换掉 `Logs/`（CI 想把日志收进构建产物目录、
单测不想污染工作区时用）：

```bash
UI_LOG_DIR=/var/log/ui-auto python run.py
```

必须在**启动进程之前**设好 —— `Common/log.py` 在被 import 的瞬间就会建日志文件。
变量的读取时机早于 `config.ini`，所以它只能是环境变量、不能写成配置项。

#### `Common/dir_config.py` / `getcwd.py` —— 路径

路径唯一定义处：`base_dir` / `testcases_dir` / `htmlreport_dir` / `junitreport_file` + `ensure_dir()`。
**新增目录时先在这里加常量再去引用**，保持路径单一来源。

#### `Common/junitReport.py` —— JUnit XML 输出（CI 相关）

`JUnitResult` 继承 HTML 报告器的结果类，额外记录**每条用例的状态与耗时**；
`write_junit_xml()` 按测试类拆分成多个 `<testsuite>`，写成 Jenkins 能解析的 XML。

**关键设计**：测试**只跑一遍**，同一份结果同时产出 HTML + XML 两种报告
（靠 `HTMLTestRunner(resultclass=JUnitResult)` 注入实现）。

自检是否合法：

```bash
python -c "import xml.etree.ElementTree as E; E.parse('Report/junit-results.xml'); print('XML OK')"
```

#### `Common/ci.py` —— CI 环境适配（CI 相关）

| 函数 | 作用 |
|---|---|
| `is_ci()` | 是否在流水线中（识别 Jenkins / GitLab / GitHub 等 8 种标记变量） |
| `build_info()` | 收集任务名、构建号、分支、提交号、被测应用构建号等 |
| `build_label()` | 生成一行构建标识，拼进报告描述 |
| `log_context()` | 把上下文写进日志 |

本地想模拟 CI：`set BUILD_NUMBER=999 && python run.py`。

#### `Common/sentMail.py` —— 邮件通知

把 HTML 报告作为附件，通过 QQ 邮箱 SMTP（SSL 465）发送。
**发信失败不会影响测试结果**（只记日志、返回 False），这是刻意设计。

单独测试：`python -m Common.sentMail`。

### 5.1 快速开始

python run.py --suite smoke

### 5.3 配置项一览（config.ini）

**先记住一条纪律（零硬编码改造后全框架统一）**：

- **业务数据**（标题文案、账号、文件路径、断言期望、报告元信息、邮件文案……）
  代码里**没有任何兜底默认值**，一律用 `Config.require` 读取 —— **没配就直接报错**，
  报错文案会指明「哪个段、哪个键、哪个环境变量」，补齐再跑（退出码 2，ABORTED）。
- **技术参数**（超时、轮询间隔、视口、目录名……）用 `Config.get / get_int / get_float`
  读取，代码里有等价默认值 —— **不配也能跑**，配置只是为了按环境调优。
- 元素定位分两层：**界面文案**（按钮文字/菜单名/placeholder 关键词）是业务数据，
  进 `config.ini` 的 `[locators]` 段；**定位策略**（怎么找）是通用代码，
  留在 `Common/elementPage.py`。换系统只改配置，策略直接复用。

| 段 | 键 | 必填? | 说明 |
|---|---|---|---|
| `[environment]` | `url` | **必填** | 被测入口地址（统一门户登录页） |
| | `browser` | 可选 | `chrome` / `firefox` / `edge` |
| `[testcase]` | `login_username` / `login_password` | **必填** | 登录账号（缺失时报错并提示 `UI_TESTCASE_LOGIN_*`） |
| | `upload_file` | **必填** | 待上传视频的绝对路径（必须真实存在） |
| | `upload_dialog_title` | 走 autoit 时**必填** | 系统文件对话框标题（中文系统「打开」/英文 Open） |
| | `query_keyword` | **必填** | 关键字查询用例（test_5keyword）的搜索词 |
| | `phone` / `reporting` | **必填** | 上传表单字段 |
| | `video_author` | 可选 | 留空自动用登录账号兜底（合理联动，不算硬编码） |
| | `upload_mode` | 可选 | `set_input_files`（默认，推荐）/ `autoit`；技术开关 |
| `[assert]` | `title_login` / `title_workbench` / `title_material` | **必填（三项）** | 断言用的期望标题**关键字**；换系统只改这里，不改代码 |
| `[assert]` | `match_mode` | 可选 | 标题匹配方式：`exact` / `contains`（默认）/ `regex`；contains 下两边去空格后比对，标题带版本号不误判 |
| `[locators]` | `btn_login` / `menu_first_level` / `field_keyword` … | 建议全配 | **元素界面文案**（按钮文字/菜单名/placeholder 关键词/组件 id）；未配的键退回技术兜底定位 |
| `[locators]` | `<键名>_xpath` | 可选 | 完整定位表达式，覆盖框架默认策略（逃生门）；支持 `${key}` 插值引用同段其它键 |
| `[case_names]` | `login` / `upload` / `submit` … | 可选 | 用例在报告里的中文名；留空显示 unittest 方法名 |
| `[system]` | `username_placeholder` / `password_placeholder` / `login_button_text` | **必填（三项，用 GenericPage 时）** | 登录页元素"文案特征"，接入新系统的第一组配置 |
| | `success_text` | 可选 | 登录成功标识文案；留空则等加载遮罩消失 |
| | `element_timeout` | 可选 | 该系统的元素超时秒数 |
| `[report]` | `title` / `filename` / `tester` / `description` | **必填（四项）** | 报告元信息；`--title` 等命令行参数可覆盖 |
| `[entrance]` | `title` | 用 `entrance.py` 时**必填** | 备用入口的报告主题（旧版写死在代码里，现在只认配置） |
| | `description` | 可选 | 备用入口报告描述 |
| `[ci]` | `headless` | 可选 | 无头开关（**流水线必须 true**） |
| | `element_timeout` | 可选 | 元素定位超时秒数，默认 15；CI 慢可调 30。Playwright 用它作为默认动作超时 |
| | `implicit_wait` | 可选 | 默认 5，保留兼容（Playwright 内建自动等待，无独立隐式等待） |
| | `retry_times` | 可选 | 操作失败自动重试次数（降低偶发失败），默认 2 |
| | `smoke_cases` | 可选 | 冒烟用例关键字，逗号分隔 |
| | `junit_xml` | 可选 | JUnit XML 输出路径；**留空自动按 `[paths]` 拼出**；传 `none` 关闭 |
| | `extra_chrome_args` | 可选 | 附加 chromium 系启动参数，逗号分隔 |
| | `chrome_binary` | 可选 | 浏览器可执行文件路径；留空 = 用自带 Chromium |
| `[paths]` | `testcases_dir` / `case_pattern` | 可选 | 用例目录与文件名匹配规则（`--pattern` 未传时用 `case_pattern`） |
| | `report_dir` / `junit_filename` / `img_dir` | 可选 | 报告目录、JUnit 文件名、失败截图目录名；改产出物位置只动这里 |
| `[tuning]` | `viewport` / `browser_locale` | 可选 | 无头视口（支持 `1920x1080` 等四种写法）与浏览器语言 |
| | `window_poll_interval` / `loading_poll_interval` / `retry_interval` | 可选 | 各类轮询/重试间隔秒数（切标签页、等遮罩、safe_click 重试） |
| | `enter_settle` / `upload_settle` / `menu_render_wait` / `switch_menu_wait` | 可选 | 交互后的稳定等待（回车前、赋值文件后、菜单逐级渲染等） |
| | `dialog_timeout` / `autoit_timeout` / `autoit_input_settle` / `autoit_click_settle` | 可选 | 原生弹窗与 autoit 对话框超时 |
| | `loading_selector` | 可选 | 「加载遮罩」特征 xpath，系统有专属 loading 类名时可整体替换 |
| | `notify_timeout` | 可选 | 群机器人 HTTP 超时秒数 |
| `[timing]` | `workbench_render` / `menu_load` / `material_render` / `upload_recognize` / `upload_progress` / `query_result` / `refresh_render` / `submit_render` / `reset_settle` | 可选 | 用例各步骤的"页面节奏"等待秒数 —— 慢环境整体调大、快环境调小提速，只改这里 |
| `[notify]` | `enabled` / `webhook` | 可选 | `enabled=true` 或 `--notify` 时推送；webhook 未配则跳过不报错 |
| | `secret` / `title` | 可选 | 钉钉加签密钥；消息前缀标题（留空自动用 `[report] title`） |
| `[sender]` | `username` / `email` / `password` | 发信时**必填** | 邮件发件人（`password` 为 SMTP 授权码） |
| | `smtp_host` / `smtp_port` | 可选 | 默认 `smtp.qq.com:465`，换邮箱只改配置 |
| | `mail_subject` / `mail_body` | 可选 | 邮件主题/正文模板，支持 `{date}` `{filename}` 占位符（旧版文案写死在代码，现在改措辞不动代码） |
| `[addressed]` | — | 发信时**必填** | 邮件收件人（键名任意，值为收件邮箱） |
| `[system_名称]` | `url`/`browser`/`username`/`password`/`headless`/`pattern` | — | 多系统配置段，`--system 名称` 时读取；缺省键沿用全局配置 |

> ⚠️ `[sender] password` 填的是 **SMTP 授权码**，不是邮箱登录密码。
> 以上任意项都可用环境变量覆盖：`UI_` + 段名 + `_` + 键名（全大写），如 `UI_ASSERT_TITLE_LOGIN`、`UI_TUNING_VIEWPORT`、`UI_TIMING_MENU_LOAD`。
> 表里所有"必填"项缺失时：runner 级缺失 → 启动即 ABORTED（退出码 2）；用例级缺失 → 该套件 setUpClass 即失败，同样判退出码 2，不会带着空值误跑或误报。

### 5.4 全量 vs 冒烟：怎么选

| | 冒烟（`--suite smoke`） | 全量（默认） |
|---|---|---|
| 覆盖用例 | `test_1login` / `test_2select_scxt` / `test_3material` | 全部 6 条 |
| 覆盖业务 | 登录 → 进系统 → 进素材库 | 加上传、查询、报送 |
| 是否写数据 | **不写**，可反复执行 | **会真实上传视频、提交报送单** |
| 建议场景 | 每次构建后自动触发 | 测试环境回归 / 发布前验证 |

冒烟集由 `config.ini [ci] smoke_cases` 定义，改配置即可调整，不用改代码。

## 六、扩展指南：怎么加用例

### 6.1 加一条新用例（操作已有的页面）

假设要在素材库里加一个"删除素材"用例：

```python
# 1) config.ini [locators] —— 加界面文案（框架自动生成定位）
#    btn_delete = 删除
#    btn_confirm_delete = 确定
#    （逃生门：策略覆盖不了时写 btn_delete_xpath = //button[@id='xx']）

# 2) PageObject/loginPage.py —— 加页面动作（不写断言，不写界面文案）
def delete_material(self):
    """删除列表第一条素材。"""
    self.click(Config.locator('btn_delete'))            # 文案来自 [locators]
    self.click(Config.locator('btn_confirm_delete'))

# 3) TestSuites/testLogin.py —— 加用例（写断言）
def test_7delete(self):
    """用例7：删除素材。"""
    case_name = self.case_names['delete']    # 中文名来自 [case_names]
    log1.info('执行测试用例：%s' % case_name)
    self.login_page.delete_material()
    # 等待时长不写死：走 [timing] 配置，缺省用代码默认 2 秒（page_wait 见 4.5）
    self.login_page.page_wait('delete_settle', 2)
    # 断言期望值同样来自配置（setUpClass 里 Config.require('assert', 'title_material')）
    self.check_title(case_name, self.title_material)
```

配套配置（`config.ini`）：

```ini
[locators]
btn_delete = 删除
btn_confirm_delete = 确定

[case_names]
delete = 删除素材
```

**注意**：方法名必须带数字前缀（`test_7...`）以保证执行顺序在既有用例之后 ——
因为它是串行链的延续。

### 6.2 加一个全新的页面

```
1. config.ini [locators]    加新页面的界面文案（按钮/菜单/输入框的关键词）
2. PageObject/auditPage.py  加一个类：class AuditPage(BasePage): ...
                            动作里用 Config.locator('键名') 取元素
3. TestSuites/testAudit.py  加一个 TestCase：class TestAudit(unittest.TestCase): ...
                            —— 文件名必须以 test 开头，否则 discover 收集不到
```

新页面要独立跑（不依赖前面的登录态）时，在 `setUpClass` 里自己开浏览器，
并复用 `LoginPage.login()` 完成登录，例如：

```python
@classmethod
def setUpClass(cls):
    cls.base = BasePage()
    cls.driver = cls.base.open_browser()
    cls.page = AuditPage(cls.driver)
    cls.page.login(*Config.get_account())     # 复用已有页面对象的登录动作
```

### 6.3 加一个新的配置项

1. 先分类（决定用哪种读取方式，这是零硬编码纪律）：
   - **业务数据**（文案、账号、路径、期望值）→ 必须 `Config.require('段', '键', '含义说明')`，
     不写任何代码默认值，没配就报错（报错文案自动带环境变量线索）
   - **技术参数**（超时、间隔、目录名、开关）→ `Config.get('段', '键', 默认值)`，
     代码里保留合理默认值，配置纯为调优
2. 在 `config.ini` 与 `config.ini.example` 的对应段里加键（写清注释、必填/可选与对应环境变量）
3. 需要布尔/整数时用 `Config.get_bool()` / `Config.get_int()` / `Config.get_float()`
   （或业务数据用 `require_int()` / `require_float()`）
4. 用例里的页面节奏等待统一走 `page_wait('键', 默认秒)`，新键加进 `[timing]` 段
5. 把新键补进本文档的 [5.3 配置项一览](#53-配置项一览configini)

### 6.4 前台改版了，元素定位失效怎么办

1. 打开 `Logs/日期/Error_Logs/*.log`，搜「没有定位到元素,定位方式：... 使用的值：...」
2. 对照 `img/日期/` 里失败瞬间的截图，确认页面结构变化
3. 在浏览器 F12 里重新取定位值，优先选**相对定位**（按 `id`、按文本、按属性），
   不要复制绝对路径
4. 改 `Common/elementPage.py` 对应一行，重跑验证

### 6.5 四项进阶能力（稳定性 / 数据驱动 / 多系统 / 群通知）

框架在通用化基础上额外提供四项工程化能力，覆盖「提升稳定性 → 数据驱动用例 → 多系统切换 → 结果通知」的完整闭环。

#### 6.5.1 稳定性：操作自动重试（降低偶发失败）

`BasePage` 的 `retry()` 与 `safe_click()` / `safe_type()`：对 Playwright 的超时
（`TimeoutError`）及其它瞬时错误（元素未就绪、点击被遮挡、页面导航中被打断等）**自动重试**，显著降低 CI 的 flaky。
（Playwright 的 Locator 永不过期，无需处理旧元素句柄失效这类问题。）

- **只重试瞬时错误**，断言错误(`AssertionError`)、参数错误(`ValueError`)**不重试**（重试也无意义）。
- 重试次数由 `[ci] retry_times` 控制（默认 2），可用 `UI_CI_RETRY_TIMES` 覆盖。
- 写新页面动作时，关键点击/输入建议用 `self.safe_click(selector)` / `self.safe_type(selector, 值)`。

#### 6.5.1b 稳定性：用例级自动重试（flaky，已接入执行链路）

整条用例因偶发问题失败时自动重跑，一次通过即算通过。与上面的"操作级重试"互补：
那个重试单个动作，这个重试整条用例。

```python
from Common.flakyRetry import flaky

class TestUnstable(unittest.TestCase):
    @flaky(retry=2)                 # 方法级：只这条用例重试 2 次
    def test_网络敏感用例(self): ...

@flaky(retry=3)                     # 类级：该类所有用例都重试
class TestSlowEnv(unittest.TestCase): ...
```

也可以全局开启：`config.ini [ci] flaky_retry = 2`（默认 0，关闭）。

**接入语义（重要）**：重试发生在结果类的 addFailure 钩子内——重试成功按成功记录、
用尽按最终结果记录，HTML 报告 / JUnit XML / 退出码三份证据**保持一致**，
不存在"报告说失败、退出码说成功"的分裂。重试次数语义是"最多再跑 N 次"
（初次 1 次 + 重试 N 次）。

#### 6.5.2 数据驱动：一条用例跑多组数据

`Common/dataDriver.py` 支持从 **CSV / JSON / Excel** 加载测试数据，把一条用例参数化展开为多条独立用例。

```python
from Common.dataDriver import data_driven, load_data

DATA = load_data('data/users.csv')   # 数据文件放 data/ 目录；也支持 .json / .xlsx

class TestLogin(unittest.TestCase):
    @data_driven(DATA)
    def test_login(self, row):
        self.page.login(row['username'], row['password'])
        # 期望标题走 [assert] 配置（setUpClass 里 Config.require 读入），不写死
        self.check_title('登录-%s' % row['username'], self.title_login)
```

- `load_data(path)` 按扩展名自动路由（CSV/JSON 开箱即用，Excel 需 `pip install openpyxl`）。
- 改数据不用改代码，同一逻辑覆盖多组账号/输入。
- **展开机制（已接入执行链路）**：`build_suite` 收集用例时会自动把 `@data_driven`
  标记的方法展开成"每组数据一条独立用例"，报告里各自计分、互不影响；
  没有该标记的用例原样通过（零开销）。

#### 6.5.3 多系统切换：一套框架管多个被测系统

在 `config.ini` 为每个系统建一个 `[system_名称]` 段，运行时 `--system 名称` 一键切换。

```ini
[system_erp]
url = http://erp-test/login
username = erp_tester
password = your_password
pattern = testErp*.py
```

```bash
python run.py --system erp            # 切到 ERP 系统，按其 pattern 选用例
python run.py --system erp --pattern testSmoke*.py   # 系统内再覆盖用例集
```

可用键：`url / browser / username / password / headless / pattern`，缺省键沿用全局配置。
命令行 `--url/--browser` 等仍可在系统配置之上再覆盖。

#### 6.5.4 结果通知：推送到群机器人

跑完把结果（通过/失败、用例数、耗时、报告路径）推送到 **钉钉 / 企业微信** 群。

```bash
python run.py --notify
```

配置 `[notify]` 段（见 5.3）：`webhook` 必填（机器人地址），钉钉若开启「加签」再填 `secret`。
发信失败只记日志、不影响测试结果，与邮件通知一致。

## 七、常见问题排查

### 7.1 「一条用例都没收集到」深度排查

本工程历史最高频的问题。根因分四大类，**先看日志再看目录** —— 现在的日志已把原因直接翻译成中文。

#### 判断口径：什么叫"没收集到"

| 退出码 | 含义 | 典型日志 |
|---|---|---|
| `2` | 环境/配置问题，**一条用例都没拿到**（本节重点） | `未收集到任何测试用例，排查结论如下：` |
| `1` | 用例拿到了，但执行失败/出错 | 失败摘要，或 `用例模块导入失败` |
| `0` | 全部通过 | `结果 : 通过（PASSED）` |

> ⚠️ 务必区分「**没收集到**」（退出码 2）和「**收集到但没跑起来**」（退出码 1、只显示 1 条且报错，见 C 类）。

#### A 类：收集阶段直接抛异常

| 触发条件 | 底层机制 | 修复 |
|---|---|---|
| `TestSuites/` 缺 `__init__.py` | unittest 只把「包」当可扫描目录，缺包标识时 `discover()` 直接抛 `ImportError: Start directory is not importable` | 补一个空的 `__init__.py`（工程已提供，**不要删除**，也不要被 `.gitignore` 排除） |
| 用例目录被整体删除 / 改名 | 同上 | 确认 `Common/dir_config.py` 的 `testcases_dir` 指向真实存在的目录 |
| 从工程目录之外启动 | `start_dir` 为相对路径时会解析到错误位置 | 一律在工程根执行 `python run.py`（`run.py` 已用 `sys.path.insert` 兜底） |

**现在的表现**：不再崩栈，日志打印「用例目录检查未通过 / 包标识文件 `__init__.py`：【缺失】」，
退出码为 `2`（符合契约：CI 标记为环境异常，而非用例失败）。

#### B 类：静默收集为 0（无报错，最难查）

共同点是 **unittest 不报错、不告警，直接跳过**，只能靠体检日志发现。

| 触发条件 | 例子 | 现在日志会指出 |
|---|---|---|
| 文件名不以 `test` 开头 | `loginTest.py` | `按 pattern=test*.py 匹配到：（无）` |
| 文件名大小写差异 | `TestLogin.py` —— **Windows 收得到、Linux 收不到** | `大小写隐患：本机匹配 [...]，Linux（Jenkins 节点）只匹配 [...]` |
| 文件名不是合法模块名 | `test-login.py`、`test login.py`、`测试登录.py`、`test.login.py` | `文件名非法（会被 discover 静默跳过且不报错）` |
| 子目录缺 `__init__.py` | `TestSuites/smoke/testX.py` | `子目录 smoke/ ：__init__.py【缺失】` + 整棵跳过说明 |
| 方法名不以 `test` 开头 | `def check_login(self)` | 不单独告警（同文件其余用例正常收集），排查时对照方法名 |
| 用例类未继承 `unittest.TestCase` | `class TestXxx(object)` | 同上 |

> **大小写那条最隐蔽**：Windows 的文件名匹配不区分大小写（`testLogin.py` 能被 `Test*.py` 命中），
> Linux 严格区分。所以「本机跑得好好的，Jenkins 上一条都收不到」通常就是它。
> 约定：**用例文件名统一小写 `test` 开头**，如 `testLogin.py`、`test_smoke_login.py`。

#### C 类：收集到了，但表现为"只有 1 条且报错"

| 触发条件 | 底层机制 |
|---|---|
| 依赖没装（如目标机器缺 `playwright`，或未执行 `python -m playwright install chromium`） | `import` 失败时 `discover()` **不报错**，而是塞一个 `unittest.loader._FailedTest` 占位对象 |
| 用例里的 `import` 写错 / 模块不存在 | 同上 |
| 用例文件有语法错误 | 同上 |

表现为「**只收集到 1 条用例，跑起来就 error**」，极易被误判成"没收集到"或"框架坏了"。

**现在的表现**：日志明确打印 `用例模块导入失败：unittest.loader._FailedTest.TestSuites.xxx` 及真实原因
（含 `No module named 'playwright'`）。若收集到的**全部**是占位对象，直接判为环境异常（退出码 `2`），
不会被误报成"业务用例挂了"。

#### D 类：执行阶段失败，被误认为"没收集到"

| 触发条件 | 曾经的后果（已修复） |
|---|---|
| `setUpClass` 抛异常（最常见：**浏览器起不来**） | `addError` 回调读取尚未初始化的输出缓冲区 → `AttributeError: 'JUnitResult' object has no attribute 'outputBuffer'`，把"浏览器打不开"的真实原因盖掉；HTML 报告只生成 **0 字节空文件**、JUnit XML 不生成、退出码被误判为 `2` |

修复内容（`Common/HTMLTestReportCN.py`）：

1. `_TestResult.__init__` 中提前创建 `outputBuffer`，不再只在 `startTest` 里创建；
2. `complete_output()` 取不到缓冲区时兜底返回空串；
3. `HTMLTestRunner.run()` 用 `try/finally` 保证**无论执行中发生什么，报告都会写出来**，不再留下空文件。

修复后：报告有内容（可直接看到 `setUpClass` 的报错）、JUnit XML 正常生成、退出码为 `1`（用例出错）。

#### 自查三步法

```bash
# ① 只看收集结果，不执行用例（最安全，不触碰被测系统）
python -c "import sys,os;sys.path.insert(0,os.getcwd());from Common.runner import build_suite;print('用例数 =', build_suite().countTestCases())"

# ② 确认目录与包标识
ls TestSuites/                      # 期望：__init__.py + test*.py
ls TestSuites/__init__.py

# ③ 直接跑，把日志中"排查结论"整段贴出来
python run.py --junit none
```

`Logs/日期/Error_Logs/` 里有同样的完整诊断。CI 上可直接搜这些关键字定位：
`未收集到任何测试用例`、`包标识文件`、`文件名非法`、`用例模块导入失败`、`大小写隐患`。

### 7.2 其它常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| 退出码 2、日志出现 `缺少必需配置：config.ini 的 [段] 键` | 零硬编码纪律：**必填业务配置没配**（如 `[assert] title_login`、`[report] title`、账号） | 按报错文案补配置（它已给出段/键/对应环境变量），或在流水线注入该环境变量；**不要**去代码里加默认值 |
| 加了 `--suite smoke` 却直接中止 | `[ci] smoke_cases` 为空 | 这是**刻意的安全保护**：冒烟集为空时若继续执行就等于跑全量、会真实写入数据，所以直接中止。补回 `smoke_cases` 即可 |
| `未配置被测地址` | `config.ini` 没有 url，环境变量也没传 | 补 `[environment] url`，或传 `--url` / `UI_ENVIRONMENT_URL` |
| 元素全部定位不到 | 忘记切标签页（点「发布系统」会新开页） | 确认调用了 `switch_other_window()` |
| 上报错 `AttributeError: 'NoneType'` | `get_element()` 找不到元素返回 `None` | 上游用例方法里先判空，或确认元素定位值是否失效 |
| 上传用例报 `FileNotFoundError` | `[testcase] upload_file` 路径不存在 | 改成真实存在的文件；CI 上该用例不在冒烟集内 |
| 无头模式下报找不到元素，有界面却正常 | 页面渲染时机差异 / 视口尺寸导致元素折叠 | 调大 `[ci] element_timeout`；视口可调 `[tuning] viewport`（默认 1920x1080） |
| 流水线上浏览器起不来 | 没执行 `python -m playwright install chromium` 下载自带浏览器 / 没开无头 | 装好依赖后跑一次 `playwright install chromium`；确认 `UI_CI_HEADLESS=true` |
| 容器里 Chromium 崩溃 | `/dev/shm` 太小 | 启动容器加 `--shm-size=2g`（已加 `--disable-dev-shm-usage` 兜底） |
| Jenkins 上看不到用例明细 | `Report/junit-results.xml` 没生成 | 检查 `[ci] junit_xml` 配置与磁盘权限；跑一次 `--junit none` 排除 |
| 中文日志乱码 | 控制台编码不是 UTF-8 | 设 `PYTHONIOENCODING=utf-8`（Jenkinsfile 已设） |
| 报告页样式错乱（Jenkins 内嵌） | HTML Publisher 的 CSP 限制 | 见 [CI-CD 接入指南](CI-CD接入指南.md) 的 CSP 章节 |

**排错优先级**：控制台「失败摘要」→ `Error_Logs` 日志 → `img/` 失败截图 → HTML 报告。

## 八、框架单元测试

### 8.1 为什么单独有一层单元测试

`TestSuites/` 里的 UI 用例要开浏览器、连真实环境、跑几分钟，而且对被测系统有副作用。
所以「改了一行框架代码，想确认没改坏」这件事，靠跑 UI 用例是非常昂贵的：

- 跑一次几分钟，反馈慢
- 失败原因混杂：可能是框架坏了，也可能是页面改版了、环境不通了
- 生产环境上跑还有数据风险

`tests/` 解决的就是这个问题：**不开浏览器、不联网、几秒跑完、零业务副作用**，
专门验证 `Common/` 与 `PageObject/` 的代码逻辑。

| | `tests/` 单元测试 | `TestSuites/` UI 用例 |
|---|---|---|
| 测什么 | 框架代码本身 | 被测系统的业务功能 |
| 是否开浏览器 | 否（用假 Page 桩 `FakePage`/`FakeLocator` 替代） | 是 |
| 是否连网络 | 否 | 是 |
| 耗时 | 几秒 | 几分钟 |
| 数据副作用 | 无 | 有（会上传视频、提交报送单） |
| 什么时候跑 | 改框架代码后**必跑** | 框架验证通过后跑 |

### 8.2 怎么跑

```bash
# 全部（推荐）
python tests/run_unit_tests.py

# 只跑某个模块（改哪个模块就单跑它，几秒出结果）
python tests/run_unit_tests.py tests.test_config
python tests/run_unit_tests.py tests.test_base_page tests.test_runner

# 产出 JUnit XML（流水线用）
python tests/run_unit_tests.py --junit Report/unit-tests.xml

# 等价的 unittest 官方写法
python -m unittest discover -s tests -t . -p "test_*.py"
```

退出码与 `run.py` 一致：`0` 全部通过、`1` 有测试失败，可直接当流水线的质量门禁。

### 8.4 测试基座：不启动浏览器怎么测框架

关键在 `tests/helpers.py`，它提供了四件套：

| 工具 | 作用 |
|---|---|
| `FakePage` / `FakeLocator` / `FakeElement` / `FakePlaywrightFactory` | 假的 Playwright 页面、定位器与浏览器入口：接口形状对齐 `playwright.sync_api`，让 `BasePage` 以为自己真的在操作浏览器，实际只记录调用，于是可以毫秒级断言"点了哪个元素、按什么顺序"（"找不到元素"用 `FakePage(find_error=PlaywrightTimeoutError(...))` 模拟） |
| `patch_config()` | 把配置来源换成临时 `config.ini`，测读写不碰工程文件 |
| `patch_dirs()` | 把 `Logs`/`img`/`Report`/用例目录重定向到临时目录 |
| `make_sandbox()` | 建一个"迷你工程"（配置 + 用例包），供 `runner.run()` 跑端到端 |

另外 `tests/__init__.py` 做了两件必要的准备：

1. **日志目录先挪走**（`UI_LOG_DIR`）：`Common/log.py` 在**被 import 的那一刻**就会建好两个
   日志文件，所以"先 import、再摘 handler"来不及 —— 工程 `Logs/` 里仍会留下 0 字节文件。
   本工程的做法是先把日志根目录指向临时目录，再让 `Common.log` 被导入。
   `tests/test_entrypoints.py` 起的子进程会继承这个环境变量，因此同样受控。
2. **日志静音**：摘掉工程 logger 的文件 handler，避免测试刷出大量无意义的 ERROR 日志
   （需要看工程日志时用 `UT_SHOW_LOG=1` 跑；想把日志留在工程 `Logs/` 下用 `UT_KEEP_LOG=1`）

三个环境变量一览：

| 变量 | 作用 | 默认 |
|---|---|---|
| `UI_LOG_DIR` | 日志根目录（生产代码支持，CI/测试都用得上） | `<工程根>/Logs` |
| `UT_SHOW_LOG=1` | 打开工程日志输出，排查单测失败原因 | 关闭 |
| `UT_KEEP_LOG=1` | 日志写回工程 `Logs/`（**会污染工作区，仅在需要留证时用**） | 关闭 |

> `UI_LOG_DIR` 是唯一进入生产代码的开关，因为单测和 CI 都需要它；另外两个只在测试基座里生效。
> 注意它必须在**启动进程之前**设好，import 之后再改无效。

### 8.5 写新测试时的三条铁律（和两个坑）

**铁律**

1. 绝不真的启动浏览器 —— 一律用 `FakePage`（经 `FakePlaywrightFactory` 桩接进 `open_browser`）
2. 绝不写工程目录 —— 配置、日志、报告、截图全部重定向到临时目录
3. 绝不连外网 —— SMTP 之类的出口一律 patch 掉

**坑一：样例 `TestCase` 会被 discover 收走**

unittest 加载测试模块时，会把模块命名空间里**所有** `TestCase` 子类都当成用例执行。
所以"用来模拟失败/出错的样例用例类"绝不能直接写在 `test_*.py` 里 ——
否则测试结果里会凭空多出几条"故意失败"。

本工程的做法：
- 样例类统一放 `tests/samples.py`（文件名不以 `test` 开头，不会被扫到）
- 引用时**必须用模块方式**：`from tests import samples` 然后写 `samples.FailCase(...)`，
  不能写 `from tests.samples import FailCase`

**坑二：需要 import 真实用例类时，用 `load_tests` 白名单**

`test_test_login_suite.py` 需要 import 真实的 `TestLogin` 来校验结构，
但上面的规则会导致 `TestLogin` 被当成用例收集 —— 那样 `setUpClass` 会被真的执行、
直接尝试打开浏览器。解决办法是在该文件末尾定义 `load_tests()`，
显式声明"本文件只执行这几个测试类"。

**附带一个小坑**：写解包时别用两个 `_` 做占位（`for _, _, value in ...`），
它们会互相覆盖，导致过滤条件静默失效 —— 本工程第一次写测试时就踩到了。

### 8.6 通过单元测试发现并修复的缺陷

| 现象 | 根因 | 修复 |
|---|---|---|
| 未配置上传文件时，最终报的是"未安装 PyAutoIt"这种莫名其妙的信息 | `upload_file()` 的回退条件过宽：把"配置缺失/文件不存在"也当成"默认上传方案失败"，降级到 autoit 后又被 autoit 的报错盖掉 | `PageObject/loginPage.py`：`ValueError` / `FileNotFoundError` 直接抛出，**只对技术性失败回退** |
| `_parse_selector()` 返回值与函数文档不符 | 定位方式不认识时只记日志就返回，把 `(None, 定位值)` 这种半成品交给调用方 | `Common/basePage.py`：改为返回 `(None, None)` |
| 配置里按"换行"写 `extra_chrome_args` 会直接解析失败 | ini 不支持 `\n` 转义，必须用缩进续行，但原注释没说明 | `Common/basePage.py`：注释澄清正确写法 |
| `setUpClass` 抛异常（浏览器起不来）时报告 0 字节、真实原因被 `AttributeError` 盖掉 | 结果缓冲区只在 `startTest()` 里创建 | 上一轮已修（`HTMLTestReportCN.py`），本轮的 `test_report_template.py` 把它锁定住，防止回归 |
| 跑一次单测，工程 `Logs/日期/` 下多出一堆 0 字节日志文件 | `Common/log.py` 在 import 时就 `new` 了 `FileHandler`，"先 import 后摘 handler"只挡得住写入、挡不住建文件；子进程（跑 `run.py`）更是完全绕不过 | `Common/log.py` 新增 `UI_LOG_DIR` 环境变量；`tests/__init__.py` 在 import 前先把日志根目录挪到临时目录 |
| 系统临时目录里越攒越多 `ut_config_*` / `ut_sandbox_*` 残留目录 | `_shared_config_dir()` 与 `make_sandbox()` 建的目录没有登记到 `atexit` 清理清单 | `tests/helpers.py` 抽出 `_register_temp_dir()`，所有建临时目录的地方统一登记 |
| 全量测试要跑 110 秒，主要是 Windows 上反复建/删临时目录 | 每个用例都 `mkdtemp` + `rmtree` | 配置目录全进程共享、其余目录登记到 `atexit` 一次性清理 → **110 秒降到 26 秒**（迁移 Playwright 后进一步降到 2 秒左右） |
| `patch_dirs()` 在设了 `UI_LOG_DIR` 时对日志目录失去作用 | 环境变量优先级高于给 `Common.log.getcwd` 打的桩 | `patch_dirs()` 进入时摘掉 `UI_LOG_DIR`、退出时还原（用 `finally`，用例抛异常也能还原） |

### 8.7 与流水线的结合

`Jenkinsfile` 已新增 `框架单元测试` stage，位于"准备运行环境"与"执行冒烟测试"之间：

- 用 JUnit XML 输出到 `Report/unit-tests.xml`，与 UI 结果一起被 `junit` 步骤解析
- 单元测试不通过会直接让构建变红，**比 UI 用例更早暴露框架层问题**

详见 [CI-CD 接入指南](CI-CD接入指南.md)。

## 九、已知限制与改进方向

### 9.1 设计层面的已知限制

| 限制 | 影响 | 建议 |
|---|---|---|
| 用例强顺序依赖，无数据隔离 | 任一步失败，后续用例连续失败 | 排错时优先修**最早失败**的那条；也可给依赖链用 `@depends_on` 让后续用例跳过；长期可考虑用接口造数据解耦 |
| 断言只校验页面标题 | 上传成功、查询命中数、报送状态等业务数据未被断言 | 逐步增加 `get_text()` 断言（`BasePage` 已提供该能力） |
| 元素界面文案靠人工维护 | 产品改字需要同步 `[locators]` | 改版后先核对 `[locators]` 与页面真实文字；定位已全面语义化，不再有绝对路径 |
| 冒烟集靠方法名关键字匹配 | 方法名改动会使冒烟集失效 | 改方法名时同步更新 `[ci] smoke_cases` |
| 被测系统为生产环境 | 全量执行会产生真实数据 | 流水线务必用 `UI_ENVIRONMENT_URL` 指向测试环境；也可用 `--env prod` 强制只读模式 |

### 9.2 可清理的遗留文件

以下三个文件全工程零引用，可在确认后删除（本次改造**未删除**，仅在此登记）：

| 文件 | 原因 |
|---|---|
| `Common/HTMLTestRunnerNew.py` | 英文旧报告模板，报告统一走 `HTMLTestReportCN.py` |
| `PageObject/homePage.py` | 空壳类，无方法、无引用 |
| `TestSuites/testHome.py` | 空模块，无 TestCase |

### 9.3 建议的下一步

1. **元素定位治理**：优先替换 `submission` / `first_trial` / `person_of_first_instance` 三条绝对 xpath
2. **断言增强**：把"标题未跳走"这类弱断言替换为业务数据断言
3. **环境分离**：在测试环境跑全量回归，生产环境只跑冒烟
4. **失败重试**：用例级 flaky 重试已可用（`[ci] flaky_retry` 或 `@flaky`），
   串行业务流的用例建议保持关闭（重试解决不了登录态丢失），独立的只读用例可放心开启
5. **测试覆盖补强**：`BasePage` 的"预留 API"（`switch_menue` / `get_elements` 等）目前只做了基础覆盖，后续启用时需补测试
